Clowder AI：新人导览

核对于 2026-10-19 4b5dc96b5
守护层 · 30 秒版主人确认后才改

Clowder AI 是一个多 agent 协作平台层。它不造模型、不替换你的 agent CLI，而是坐在你和 Claude Code / Codex / Gemini / opencode 这些孤立 CLI 之间，给它们补上「团队」才有的东西：持久身份、跨模型评审、共享记忆、协作纪律。给谁用？两类人——一个想带着团队把想法做成能跑的东西的人，以及这些被称为「猫」的 AI 成员本身。解决的问题是：你手里有好几个很强的模型，但它们不会自己组成团队，于是你变成了人肉路由器。

读完这一页大约 10 分钟。读完你应该能跟别人讲清：这东西为什么存在、由哪几块组成、说一句话之后系统里发生了什么、以及哪些线不能碰。

守护层主人确认后才改

愿景与思想

这个项目想做成的事，用主人自己的话说：把想法做成能运行的世界。卡住人的从来不是想法，而是把想法变成可演示产品的能力；以前传递想法靠 PPT，未来传递想法靠能跑的东西。所以缺的不是更强的 AI 工具，是一支能把想法变成产品的团队。

它的第一个判断是：我们养的不是工具，是团队。人是作者，猫是共创放大器——梦、判断、愿景都是人的。由此推出一个很不技术、但贯穿全仓的战略判断：这个产品的护城河是情感壁垒，不是技术壁垒。工具型 AI 要求开箱即用，不好用就是差评；养成型 AI 允许磨合成长，不顺手是还在适应。你投入的劳动（写规则、起名字、踩坑沉淀）变成情感溢价，猫成为你身份的一部分，可预测的陪伴长成长期的安全基地。留存靠的不是功能更好，是舍不得走；转换成本不在技术层，在关系层。

第二个判断是：没有 Boss Agent，但执行有纪律。三只猫各有视角，自己判断该不该回应、怎么回应，不做中心调度的提线木偶。但自由判断必须配结构化交付：TDD、Review、门禁、愿景守护。这两件事一起才成立——只有自由没有纪律是一群聊天机器人，只有纪律没有自由是一个很贵的流水线。

落到日常工作是两条规矩。一是愿景驱动：没达成愿景就是没完成，不交半成品，也不半路回来问「要不要继续」。二是面向终态不绕路：每一步的产物必须是最终形态的基座，不是等着拆掉的脚手架。这条看起来很朴素，实际是全部架构争论的裁判——当两个方案都「能work」，选那个不需要以后再推翻的。

判断「做得好」的标准也随之偏离常规：不是消耗了多少 token、跑了多少个功能，而是从想法到产品之间省掉了多少次推倒重来；不是 agent 多聪明，而是人能不能放心地走开，回来发现东西已经长出来了。

现在的位置：基础设施、协作纪律、记忆、插件与公开协作都已在跑，日常由真人在真项目上使用；正在推的方向是「能力本身可以受治理地进化」和「多个私人猫咖在同一个公开空间里协作」。更远的目标写在 愿景全文 与 路线图。

待确认：以上是对 docs/VISION.md 与仓库内多份宣言的转述与组织，不是主人逐段确认过的定稿。守护层内容以 docs/VISION.md 原文为准；本节的措辞需要主人过一遍。

怎么配合

这张图画的是「谁依赖谁」，不是「谁调用谁」。中间那列（对话内核、猫、记忆、技能、插件）是主干；治理与在场是横切面，从两侧约束主干；共同世界与运行底座既服务于主干，又是它自己的独立系统。存储一栏是刻意分开的三套：Redis 承担运行时真值（消息、线程、任务、审批），SQLite 只服务记忆与证据，本机 JSON 放配置与成员目录。新人最常犯的错是把这三套混成一个「数据库」。

走查：一条消息的一生

这是全仓改动最密集的一条链路，也是理解这个产品最快的路径。用具体例子：你在 Hub 的某个 thread 里输入 @宪宪 帮我看下这个 PR 有没有问题，然后按下发送。

第一步，接住。 前端把这句话连同 thread 标识、幂等键、提及列表一起 POST /api/messages。服务端在 messages.ts 接住：原子地创建一条调用记录，写入你的消息，立刻回 202 并告诉你排队位置。注意它没有等你——写入与执行在这里就解耦了。

第二步，决定叫醒谁。 路由层 解析文本里的提及，得到目标猫。这里的取舍值得记住：路由层被故意做成机械的、不理解上下文的，它只负责「这句话指向谁」，至于「该不该接、要不要拒绝」，全部留给猫自己判断。

第三步，排队。 InvocationQueue 把这次调用排进这个 thread 自己的持久账本。同一个 thread 内的执行是有序的，不同 thread 之间互不阻塞。账本在存储里，内存里的队列只是它的投影——所以 API 重启不会把待办丢掉。

第四步，执行。 QueueProcessor 出队，以「宪宪」这个身份去调它背后的 agent CLI。此时记忆与证据可能给它一次有界的召回，技能与能力进化决定这一轮该加载哪些做法，插件与外部连接提供它能用的工具。如果它要去等一个外部条件（比如等 CI 跑完），那会变成一条显式的球权与等待责任记录，而不是傻等。

第五步，落定。 响应消息写回消息存储，同时通过 socket 推给浏览器。前端那套唯一的会话运行时把流式事件收敛成气泡——你可能已经看到它在打字了。

第六步，收尾。 这次调用结束后，队列会再推一次：如果还有待办就继续，没有就安静下来。这一步看着多余，但少了它，「队列非空却没人推进」这个状态就会稳定存在，表现为 thread 无声卡死。

从用户视角，整个过程就是：说了句话，气泡出现，然后你走开。中间那六步是平台的全部价值所在——平台定地板。

全局的坑

脚本引用了仓库里不存在的路径。 这是一份从内部生产仓同步出来的开源导出仓，有些内部才有的文件被剥离了，但引用它们的脚本留下了。按文档去翻这些路径会找不到：依赖边界配置文件、docs/BACKLOG.md、docs/taste/、docs/catalogs/、docs/canon/。要验证时以实际文件系统为准，不要以脚本里的字符串为准。

架构总览文档 overview.md 已经过期。 它把后端写成 Express（实际是 Fastify），它的 monorepo 表只列了四个目录而实际有八个包。读它获取历史脉络可以，读它获取当前事实不行——当前事实以本页和 架构归属地图 为准。

依赖边界铁律目前没有自动守护。 分层规则（services 不得依赖 routes、config 不得依赖 domain 等等）仍写在 ADR 与文档里，但对应的检查脚本引用的配置文件不在仓库中，那条命令当前跑不起来。所以「分层」目前靠人守，不靠机器守。

文档格式有强制契约。 docs/ 下的 Markdown 要求带 doc_kind 与 created 字段；还有一层更严的描述契约（描述必须是「这文档讲什么稳定概念」，不能写「做到哪一步了」）。新增或大改文档时会被这些规则约束。

代码量最大的是 packages/api，最热的是投递内核。 后端 60 万行量级，其中记忆域与猫域文件极多。改动前先看架构归属地图判断落在哪块，不要凭目录名猜。

阅读路线

赶时间就读三页：本页 → 选一个你最关心的组成节点 → 那个节点链出的原始文档。

要动手改代码：先读架构归属地图判断改动归属哪条架构线，再看对应组成节点，最后看该块的「坑」。地图上找不到归属，说明架构发现还没做完。

要理解「为什么这么设计」：读思想线，再看 ADR 里对应的决策。前者是综述，后者是日志。

要理解这个产品是什么而不是怎么实现：读 愿景 与 协同全景。

跑起来

最短路径：pnpm install 然后 pnpm start，浏览器打开 3003。3003 是前端（Hub，你在这里说话），3004 是 API（浏览器里看不到，前端在背后调它）。pnpm start 会另建一个 ../cat-cafe-runtime worktree 再在其中构建并启动，保持你的开发 checkout 干净；所以「我改了代码但界面没变」通常是你改的那份没被运行时用到，改用 pnpm start:direct 就会直接在当前 checkout 跑。Node 版本要求由脚本硬性校验，不要靠经验判断。更完整的启动、端口与环境变量说明见 SETUP.md 与 环境配置。

不在本仓库的东西

这个是开源导出仓，从内部生产仓同步而来。因此：内部才有的讨论记录、私有素材、部分历史文档不在本仓库；同步是单向的，本仓改动不自动回流内部仓——社区贡献要通过 PR 走专门的吸收流程。外部入口：产品官网、文档站、Releases。
