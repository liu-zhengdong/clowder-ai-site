插件与外部连接

核对于 2026-10-19 4b5dc96b5上一层 · Clowder AI：新人导览packages/api/src/domains/plugin/packages/mcp-server/src/packages/api/src/domains/signal-intake/packages/api/src/domains/github-signals/packages/api/src/domains/community/
30 秒版

猫要干活就得能碰外面的世界——读写文件、调工具、收发 IM 消息、看 GitHub 上的 PR 和 issue。这一块是它的手：一个 MCP 工具面、一个插件框架、几类外部信号入口，以及由此长出来的社区运营。所有对外动作在这里被授权、被审计、被限界。

边界

负责：MCP 工具的定义与暴露层级、插件包的发现/安装/授权/执行、IM 与设备渠道的接入、外部事件（GitHub PR/issue、会议、消息）的准入与路由、以及社区协作对象的生命周期。

不负责：谁有资格下令（那是 猫与身份 与 协作纪律与治理 的授权面）；内容怎么被编辑和审阅（那是 共同世界与运行底座 里的协作内容面）；记忆怎么写（记忆与证据）。

块内组件

部分一句话什么时候读文档
MCP 工具面猫能调用的工具的语义身份、暴露层级与生死治理加/删/改工具，或判断某工具该不该暴露mcp-server, mcp-surface-governance cell
插件框架插件包的发现、安装、激活、Broker 会话、受监督执行与授权做插件、查「插件装了为什么没跑」domains/plugin, plugin-architecture
外部信号准入外来的事件先被准入、再被路由成工作接一种新的外部事件源signal-intake, signal-intake cell
GitHub 事实PR / issue 的采集、快照与等待谓词（只采事实，不裁决责任）「等这个 PR 合入」这类等待github-signals, github-signals cell
社区运营社区事件账本、对象状态机与收尾不变式处理外部 issue / 社区协作domains/community, community-ops cell
对外动作面对外部系统的 typed 动作、权限、审计与 dry-run让猫去操作外部系统action-plane cell

怎么运转

这块的共同模式是 准入先于动作。外部世界来的东西不会直接变成系统里的动作，而是先经过「这算不算一件事、能不能接」的判断；反过来，系统对外做的动作也要经过授权和留痕。两头都设关卡，是为了让「猫被一条伪造的外部消息指使去做危险操作」这种事故在结构上不成立。

坑

为了接一家新服务去改核心的路由和类型联合 → 每加一家都要动核心，越加越脆 → 新增外部能力走插件声明，核心只认契约。

让「采集到事实」直接等于「判定责任」 → 采集层开始做业务裁决，之后没人说得清某个状态是谁定的 → 采集只出事实与谓词，裁决留在拥有该责任的那一块。

工具暴露了两套等价入口 → 同一语义有两个名字，调用方各用一套，治理和审计永远对不齐 → 语义身份唯一，切换要原子完成，不留双暴露面。
