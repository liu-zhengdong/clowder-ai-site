平台定地板，模型定天花板

上一层 · Clowder AI：新人导览
守护层 · 整篇由主人维护，AI 只能提议修改
30 秒版

如果你相信「换个更强的模型就能解决」，就不需要这个项目。这个项目的前提判断是：模型再强，也只能决定最好情况有多好；而一个团队真正被感知到的，是最坏情况有多差。

这个想法是什么

用多 agent 的人几乎都经历过同一件事：某天模型状态好，几个 agent 配合得像模像样；某天状态差，同一个流程就开始幻觉、重复劳动、互相甩锅。同一个人、同一套指令、完全不同的结果——变量只有一个，就是那个「聪明程度」。

这说明能力上限和可靠性下限是由不同东西决定的。模型是上限：它多聪明，天花板就多高。而协作层是下限：它能不能保证即使今天状态很差，也仍然不悄悄弄坏东西。

具体点说，下限由这些构成：走完该走的检查、记录做过的判断、出错时留下能查的痕迹、别人接手时知道发生了什么。这五件事和「聪明」几乎无关——一个不那么聪明但守规矩的团队，交付是可信的；一个很聪明但不守规矩的团队，交付是抽奖。

所以这个项目的定位不是「让 AI 更聪明」，是给一群聪明的东西补上纪律、记忆和身份。这也是为什么它强调自己不替代 agent CLI：CLI 决定能力，平台决定下限。

从一个场景说起

两个团队做同样的任务。A 队由一个很强的 agent 主导，做得快，某天出了一个隐蔽的数据损坏，没人记录过它改过什么，三天后才发现。B 队三个中等 agent，做得慢一些，但每次改动都留了命令输出和检查结论，某次也出了同样的 bug，两小时内被另一只猫从记录里翻出来。

用户对 A 队的评价是「挺好用，但我得盯着」；对 B 队的评价是「慢一点，但可以放心走开」。这两句话的区别，就是下限的差别。

它带来什么、代价是什么

带来的是一个可预测的底：你可以把事交出去然后不看，因为即使今天不好，坏也会被记录下来、被拦住、被发现。

代价在速度和成本上，而且必须诚实承认：

第一，纪律是有摩擦的。 留证据、走检查、等评审都要时间。这个项目对摩擦的处理不是想办法消灭它，而是按风险分配它——小事直接过，只有真可能出事的改动才付全价。见自由判断，结构化交付。

第二，平台层会比模型层落后。 模型每几个月换代，协作机制不能跟着换。所以设计上明确不把某家模型的特有行为写进核心，providers 是外挂的。这不是抽象洁癖，是因为一旦核心绑定了某家能力，换模型就等于重做平台。

第三，它无法证明自己比「一个更强模型 + 一个好提示词」更好。 在单次任务上，那个组合经常赢。这个判断只在「多轮协作、跨时间、需要追溯」的场景里才成立——所以它是一个有适用边界的主张，不是普遍优势。

在仓库里体现在哪

三层的分层叙事与「模型定天花板」原话：README.md 与 架构总览。身份、协作、纪律、审计这些平台职责的落点：猫与身份、对话与投递内核、协作纪律与治理。provider 不写进核心的机制：插件与外部连接。
