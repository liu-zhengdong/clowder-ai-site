对话与投递内核

核对于 2026-10-19 4b5dc96b5上一层 · Clowder AI：新人导览packages/api/src/routes/messages.tspackages/api/src/domains/cats/services/agents/invocation/packages/api/src/domains/cats/services/agents/routing/packages/api/src/domains/messaging/packages/api/src/domains/cats/services/stores/packages/web/src/hooks/useSendMessage.ts
30 秒版

Clowder 里一切协作都长在 thread 上，而 thread 里发生的一切都是消息。这一块负责「一条消息怎么从你的输入框走到猫、再走回来变成气泡」——HTTP 入口、@ 路由、按 thread 的队列账本、执行器、消息存储、以及前端那套唯一的会话运行时。它是全仓改动最热的地方。

边界

负责：用户消息的接收入口与幂等、@ 提及到目标猫的解析、按 thread 持久化的排队与出队、一次 invocation 的执行生命周期、消息的 canonical 写入、provider 事件到用户可见气泡的投影、以及浏览器端渲染与实时推送。

不负责：谁该负责推进下一步（交给 球权与等待责任）；猫是谁、用什么模型、什么人格（交给 猫与身份）；消息里提到的历史知识（交给 记忆与证据）。猫与猫之间的 @ 也走这里的路由，但它只是路由，不是责任判定。

怎么运转

这张图的关键取舍是写入与执行解耦：接住消息、回执 202、后台执行三件事分开，所以界面不会因为猫跑得慢而卡住，也不会因为浏览器关掉而丢掉一次委托。代价是「已接受」和「已完成」之间多了一个需要持久化的状态窗口——那个窗口就是下面队列账本要负责的东西。

分步走一遍，就是根节点那条走查：你按下发送 → messages.ts 接住并立刻回 202 → AgentRouter 决定叫醒谁 → InvocationQueue 把它排进这个 thread 的账本 → QueueProcessor 出队并以那只猫的身份调起 CLI → 响应写回 MessageStore → socket 推送 → 气泡出现。

坑

在 QueueProcessor 之后就不再 drain 一次队列 → 队列非空却没人继续推进，thread 静默卡住，直到下一次有人说话才恢复 → 每次 onInvocationComplete 之后都要再 drain 一次，让「队列非空且无 drain」这个状态不可能稳定存在。

以为消息序号（seq）是持久真相 → 序号是每实例内存态、按单实例部署假设生成，重启后从 1 重新计数（靠实例 epoch 让前端察觉重启并重新对齐）→ 序号只用于实时推送的排序与补洞，需要持久顺序时读存储，不要拿 seq 当主键或时间线。

把消息追加当成「先读后写」 → 并发追加时丢失或重复（历史上就是 feat: complete unified message delivery lifecycle 之前的一类事故） → 追加要走存储层的原子 + 幂等路径，不要自己在业务层拼「读-合并-写」。

在前端组件里改「显示什么」 → 越过投影层直接拼装气泡内容，结果同一条语义事件在历史回放和实时推送里长得不一样（历史走服务端存储、实时走 socket），且每次改文案要动两处 → 分清两层：packages/web/src/components/ 下的 ChatContainer / ChatMessageRow / ChatMessage 只决定怎么画（布局、间距、折叠、主题），气泡内容本身由气泡投影产出；要改内容去 bubble-pipeline 那条线。渲染的跨消息投影键在 chat-timeline-projection-key.ts，别为了让内容更新去撑大它——那会让历史气泡失去记忆化。

不传 threadId 就发消息 → 消息落到名为 default 的大厅 thread，看起来「发出去了」但不在你以为的会话里。在前端它更隐蔽：default 恰好是「新会话首页」的判据（ChatContainer 里 threadId === 'default' 时渲染落地页），所以你会在首页看到一条属于大厅的消息，而不会看到它挂在某个会话上 → 所有调用方都显式带上 threadId，只有大厅场景才用 default。
